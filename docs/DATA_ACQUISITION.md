# Data acquisition and API checklist

## Start here

An API is a service you call. Download small **data extracts** and prepare them for the website. There is no need to purchase or download an API. The API key on api.nasa.gov is unnecessary for this design. Earthdata Login is a separate account used for the authenticated data products. The handed-off files contain no usable key. If the old key is still active, replace it before using it elsewhere and remove it from the original Canvas before sharing that file.

The team can begin the build with the included weather and boundaries while a second person obtains the satellite clips and tabular extracts. Here is the exact division between bundled files, additional evidence and optional shortcuts.

## Access and optional services

- **NASA Earthdata Search and CMR Search/STAC** discover NASA collections and granules by short name, AOI and dates. Catalog queries are generally public. For data files, sign in to Earthdata Login and follow the collection/DAAC authorization and HTTPS download instructions. A browser session or local Earthdata authentication suffices for the initial pilot. Keep tokens local. [Earthdata Search](https://search.earthdata.nasa.gov/search), [CMR API](https://cmr.earthdata.nasa.gov/search/site/docs/search/api.html), [Earthdata Login](https://urs.earthdata.nasa.gov/)
- **NASA AppEEARS** is an optional subset processor. Use the web UI right away or its authenticated task API for automation. Submit only products and layers in its current catalog. Jobs are asynchronous. Download their CSV/GeoTIFF and QA files and preserve task IDs. It does not cover every product in this plan. [AppEEARS API](https://appeears.earthdatacloud.nasa.gov/api/)
- **Google Earth Engine** is an optional acquisition path. The JavaScript Code Editor or Python client can reduce selected SMAP, MODIS or IMERG collections and export results to Drive. It requires a registered Google Cloud project with Earth Engine API enabled, proper access, and collection-specific checks. Keep Earth's public-facing viewer independent of this account. Verify each proposed layer in the official catalog or use direct data access, especially the CSIRO grid. [Earth Engine access](https://developers.google.com/earth-engine/guides/access)
- **NASA GIBS/Worldview** can show supplementary keyless WMTS imagery as available. Check layer IDs, matrix set, projections and date dimensions. Keep local AOI scenes for the repeatable demo. Use GIBS browse tiles as visual context and track quantitative values from the underlying products. [GIBS API guide](https://nasa-gibs.github.io/gibs-api-docs/)
- **Queensland SILO, Bureau of Meteorology and flood mapping** are validation or supporting sources. Sample documented local stations and events and record access/attribution. Queensland land-use masks or a DEM can add context later. The planned 3D heights represent data values. [SILO](https://www.longpaddock.qld.gov.au/silo/) and [Bureau of Meteorology](https://www.bom.gov.au/)
- **Comparisons from earlier notes.** GEOS-S2S, Open-Meteo and ECMWF are candidates only if the project adds an actual forecast. GLDAS, ERA5, GRACE-FO, SoilGrids, NOAA inputs and separately acquired Landsat products are alternatives or research ideas. ORNL DAAC REST subsetting and Giovanni are optional extraction routes when their catalogs cover the needed product. This build uses HLS for imagery and the locally processed products in the table.
- **Transfer and runtime.** Google Drive upload/download works in the browser and needs no Drive API setup. The prototype can use an offline geometry basemap with ordinary web packages. OpenAI API, Maps API, hosting API and paid map tokens are unnecessary for the planned source ZIP. Any deployed authenticated data refresh would require a configurable backend/worker and the specific provider's credentials. [Google Drive upload](https://support.google.com/drive/answer/2424368)

## What to do in parallel

1. **Set the geography first.** Build against all four bundled weather locations. For the first end-to-end satellite demonstration, take one supported Toowoomba-area AOI, matching masks and CRS between visits. For imagery and water mapping, choose a documented wet event and a nearby pre-event date after confirming data availability. Check the actual acquired-date footprint before choosing the pitch story.
2. **Get one clip per map type before batch processing.** Download a valid OPERA before/event pair and 2–4 aligned HLS scenes. Use Earthdata Search with a polygon or tight bounding box, date range, collection and sensor. Store WTR and mask classes for water and RGB/QA for vegetation. Export compact overlays, legends and metadata.
3. **Prepare the series.** Acquire GPM and SMAP for the selected region. Start with a 90-day demonstration period and equivalent reference periods across valid historical years. Work toward 2016–2025, or the compatible per-product subset with clearly stated coverage. Add one MOD13Q1 series, matching CSIRO pH and clay samples/clips, and at least one usable ECOSTRESS/ET period where coverage permits. Avoid bulk archive downloads and limit raw files to the pilot dates and areas. Short spans support a demo but may lack the historical sample for an anomaly or percentile.
4. **Package and integrate.** Convert to the runtime contract in WEBSITE_PLAN.md. Include date, QA, coverage, native resolution and exact source IDs. Align corresponding overlays to the same extent. Do not upsample coarse grids to imply higher precision. Retain raw data pointers and derived artifacts. Feed the real data pack into the same app and verify layer dates, source labels and calculations. Expand geographic coverage only as the team needs it.

The handoff already includes 10 years of POWER history per location and LGA geometry. The other inputs are acquisition tasks. Live POWER was checked without a key using the weather-date downloads. Earthdata credentials, individual satellite granules and ET/soil coverage still need to be checked for the chosen event.
